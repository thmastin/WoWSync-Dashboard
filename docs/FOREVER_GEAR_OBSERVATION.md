# Forever gear observation slice

The first Forever allocation-parity entry point is deliberately observation-only. For Forever 1.60.1 build 70291 / interface 16001, it reports observed equipped slots and carried items from the selected character's own version-scoped snapshot. Exact WOWSYNC item references, including variants, are retained where present.

The SavedVariables bridge also carries the matching character's structured `WoWSyncDB` equipment, bags, bank, and item-metadata sections. The Dashboard admits this sidecar only for the exact Forever profile when its character identity and export timestamp match the parsed export. Equipment and carried rows are read from those structured sections when available, so each row stays paired with that section's own `observedAt` timestamp; the text snapshot is a labeled fallback when the section is absent. Duplicate text exports may attach newer structured section observations, with newer timestamps winning and same-time conflicts retaining the first evidence.

No current Forever item metadata facet establishes equipment location. Therefore carried items are not promoted to equipment candidates. Candidate classification, eligibility, build suitability, upgrade status, and transferability remain UNKNOWN. A carried or higher-level item does not become an upgrade, location does not establish transferability, and no Retail rules are applied. Bank contents absent from the snapshot remain UNKNOWN, not empty. The existing Dashboard identity key has version, realm, and character name but no WoW account identifier; the result explicitly marks account scope UNKNOWN and only identifies the Dashboard import context. It does not assert Battle.net or WoW account membership.

The WoWSyncDB source character GUID is retained as snapshot identity evidence. If snapshots under one Dashboard version/realm/name key have missing GUIDs or conflicting GUIDs, the API/MCP and UI withhold inventory instead of selecting or combining a source character. This intentionally means legacy Forever history without GUID evidence can suppress the current view until new, consistently identified history is available. Same-text duplicate imports with conflicting GUIDs preserve a conflict marker instead of dropping the second identity.

The UI entry point is the Forever character detail card. MCP clients can call `get_forever_gear_observation` with explicit `version: "forever"`, character name, and realm. REST clients can read `/api/characters/:identityKey/forever-gear-observation`. Neither path changes the LLM provider or creates a separate allocation store.

Next validation requires a real Hallo capture through the upgraded WoWSync bridge, confirming the matching 70291 structured sections and their timestamps arrive with the exact export and render with the same freshness. This slice is not full Forever gear-allocation parity.
