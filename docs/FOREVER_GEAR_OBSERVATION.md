# Forever gear allocation evidence path

Forever 1.60.1 build 70291 / interface 16001 has a version-scoped evidence path through the existing Dashboard core. Its current live-validated inputs are the matching WoWSyncDB identity/GUID, equipment, carried bags, and exact-item GetItemInfoInstant/IsEquippableItem samples. Equipment, bags, item evidence, bank coverage, timestamps, and freshness remain separate. Structured WoWSyncDB records are accepted only when the client profile, character identity, GUID history, and export timestamp agree.

## Observation and item facts

`get_forever_gear_observation` and `GET /api/characters/:identityKey/forever-gear-observation` expose exact observed equipment and carried itemStrings. A carried row is located in the exporting character's bags, with its exact bag/container slot and stack count when observed. Location does not establish ownership. The WoW bag `isBound` facet is exposed separately as observed true/false or UNKNOWN. That facet alone never proves transferability. Missing bank capture stays UNKNOWN, not empty. Character and account identity are distinct: the existing character identity key has no WoW account ID.

Candidate classification is derived only from exact itemString-matched Forever item APIs. A `POTENTIAL_EQUIPMENT` label does not establish character eligibility, build suitability, or upgrade value. Never use Retail rules. The current Hallo live capture validated one Mining Pick candidate (item 2901) and its Forever type/equip-location facts. It did not validate any eligibility, effective stats, upgrade, or transfer conclusion.

The deployed GearExport capture added exact-variant `C_Item.GetItemInfo` tuples and bounded `C_Item.GetItemStats` tables. Hallo's 2026-10-09 capture (SavedVariables SHA256 `57F5288D433064630D4B6D08A8B79F4C13F87F2B72C5A7B25C617AE71D72F3F1`) confirms 18 GetItemInfo returns and a stats table for all 30 item variants. The returned hyperlink preserves each exact itemString; item name, class, subclass, equip-location, class/subclass IDs agree with GetItemInfoInstant; equipped item/required levels agree with structured equipment where both are present. These selected tuple fields are now live-corroborated for build 70291 and may support a separately reported required-level gate. GetItemStats keys and numbers remain raw: no conversion into effective stats, build value, or upgrade conclusions is validated.

On the same capture, the only potential-equipment candidate is Mining Pick (item 2901). Its required level 1 is below Hallo's observed level 8. That establishes only the level gate. The captured `IsEquippableItem` result also returns true for projectile ammunition, so it is not used by itself as an eligibility rule; projectile candidates remain excluded by item type. Weapon skill lines are preserved as observations and do not prove proficiency. Binding facets are captured for carried rows but do not prove transferability. Bank remains UNKNOWN.

## Cross-character assessment

`get_forever_gear_allocation` and `GET /api/characters/:identityKey/forever-gear-allocation` are a read-only decision-support view over the Forever Dashboard import context. AccountContext embeds the same core result under each Forever character in AccountContext schema 6. The selected recipient includes its latest observed class, level, equipment, and freshness. Potential item sources preserve their source character, carried/bank completeness and timestamps, exact item variants, carried locations, and binding facets. Carried location is not promoted into an ownership claim; ownership and transferability remain UNKNOWN.

The result keeps eligibility, suitability, upgrade status, transferability, and allocation priority independent. Fresh, exact-variant GetItemInfo evidence can establish a separate required-level gate; the current observed candidate meets Hallo's level gate. Weapon skill lines remain raw observations, and item statistics are compared only by matching raw key after exact-link contract and per-source freshness gates pass. Such a comparison is not an upgrade verdict. If Forever-specific evidence is missing, other dimensions stay UNKNOWN and the decision is `NO_RECOMMENDATION`, with concrete missing-evidence reasons. Characters in one Dashboard import context are not asserted to share a Battle.net account. Presence in another character's inventory is not access or transferability. Unobserved bank rows are not enumerated, treated as empty, or ranked. No opaque score or transfer action is generated.

## External API research used

The 2026-10-09 implementation pass checked version tags and contracts in the [Warcraft Wiki `C_Item.GetItemInfo`](https://warcraft.wiki.gg/wiki/API%3AC_Item.GetItemInfo), [`GetItemInfoInstant`](https://warcraft.wiki.gg/wiki/API%3AC_Item.GetItemInfoInstant), [`GetItemStats`](https://warcraft.wiki.gg/wiki/API%3AC_Item.GetItemStats), [`GetItemStatDelta`](https://warcraft.wiki.gg/wiki/API%3AC_Item.GetItemStatDelta), and [`IsEquippableItem`](https://warcraft.wiki.gg/wiki/API%3AC_Item.IsEquippableItem) pages. These pages explicitly list Forever 1.60.1 for the APIs noted. They informed tuple cross-checking, exact-link handling, the distinction between item type/equip-location and character eligibility, and continued separation of raw stat data from recommendation logic. The current GearExport candidate records `GetItemStatDelta` for each bounded carried/equipped exact-item pair in candidate-first order. The API is listed for the target build, but its result shape, direction, and agreement with GetItemStats still require live validation.

The latest Hallo capture directly confirms the GetItemInfo tuple length, exact hyperlink, selected tuple/GetItemInfoInstant agreement, raw GetItemStats tables, and the surprising `IsEquippableItem=true` result for projectile ammunition. It predates the new GetItemStatDelta candidate, so that result has not yet been observed on Hallo. The API documentation does not turn those observations into class restrictions, effective stats, equip legality, or transfer routes. The GetItemInfo `bindType` slot remains exposed as raw evidence rather than mapped to a transfer conclusion. The Wiki's [binding guide](https://warcraft.wiki.gg/wiki/Binding) describes game rules generally; it does not prove transferability for a particular Forever item or account route.

[Blizzard's UI source](https://github.com/Gethe/wow-ui-source) was checked for item-loading patterns; its current `ItemMixin` treats several item fields as cache-dependent and supports asynchronous continuation. That current source is not the Forever 1.60.1 source tree, so its load behavior is a caution, not a target-client contract. [Pawn's comparison code](https://github.com/VgerMods/Pawn/blob/main/Pawn.lua) uses explicit equipment-slot mappings and separate Classic handling, while its [license](https://github.com/VgerMods/Pawn) is CC BY-NC-ND 3.0. No Pawn code or slot rules were copied. The implementation preserves raw item facts and withholds slot alias, off-hand conflict, weapon proficiency, and build conclusions until those rules are validated for Forever.

## Identity and version safety

The source character GUID is checked across imported snapshots. Missing or conflicting GUID history withholds source observations. The model is hard-gated to Forever 1.60.1 build 70291 / interface 16001; other versions do not enter this evaluator. Retail gear-allocation logic is not called.

## Live-validation boundary

Automated fixtures validate candidate-source resolution, freshness, raw-stat comparison boundaries, binding/location provenance, UNKNOWN handling, AccountContext/REST consistency, and MCP contracts. The 2026-10-09 capture was imported into a temporary development database and REST, AccountContext, and MCP returned consistent item observations and assessments. Eligibility beyond the observed required-level gate, active build suitability, effective-stat and weapon comparisons, transfer routes, account membership, and allocation ranking remain UNKNOWN pending version-accurate evidence. Raw same-key weapon values may be displayed as comparisons, never as an upgrade score.
