# Forever gear allocation evidence path

Forever 1.60.1 build 70291 / interface 16001 has a version-scoped evidence path through the existing Dashboard core. Its current live-validated inputs are the matching WoWSyncDB identity/GUID, equipment, carried bags, and exact-item GetItemInfoInstant/IsEquippableItem samples. Equipment, bags, item evidence, bank coverage, timestamps, and freshness remain separate. Structured WoWSyncDB records are accepted only when the client profile, character identity, GUID history, and export timestamp agree.

## Observation and item facts

`get_forever_gear_observation` and `GET /api/characters/:identityKey/forever-gear-observation` expose exact observed equipment and carried itemStrings. A carried row is located in the exporting character's bags, with its exact bag/container slot and stack count when observed. Location does not establish ownership. The WoW bag `isBound` facet is exposed separately as observed true/false or UNKNOWN. That facet alone never proves transferability. Missing bank capture stays UNKNOWN, not empty. Character and account identity are distinct: the existing character identity key has no WoW account ID.

Candidate classification is derived only from exact itemString-matched Forever item APIs. A `POTENTIAL_EQUIPMENT` label does not establish character eligibility, build suitability, or upgrade value. Never use Retail rules. The current Hallo live capture validated one Mining Pick candidate (item 2901) and its Forever type/equip-location facts. It did not validate any eligibility, effective stats, upgrade, or transfer conclusion.

The deployed GearExport capture added exact-variant `C_Item.GetItemInfo` tuples and bounded `C_Item.GetItemStats` tables. Hallo's 2026-10-09 SavedVariables file (SHA256 `2DD3096020CAE3E680DFB87E47EC33728A857260B565D681EBFE11C342E0D482`) contains 38 exact item API rows; all returned GetItemInfo tuples have 18 returns and all rows have a GetItemStats table, though many are empty. The returned hyperlink preserves each exact itemString; item name, class, subclass, equip-location, class/subclass IDs agree with GetItemInfoInstant; equipped item/required levels agree with structured equipment where both are present. These selected tuple fields are live-corroborated for build 70291 and may support a separately reported required-level gate. GetItemStats keys and numbers remain raw: no conversion into effective stats, build value, or upgrade conclusions is validated.

On the 2026-10-09 build 70291 capture, the only potential-equipment candidate is Mining Pick (item 2901), exact itemString `item:2901::::::::9:1485::14:::::::`. Its required level 1 is below Hallo's observed level 9; that establishes only the level gate. The candidate's raw damage-per-second value is 1.5 versus 1.875 on the observed main-hand item, and the sampled `GetItemStatDelta` agrees with candidate-minus-equipped arithmetic. Pair coverage is partial and equipment coverage is partial, so the overall upgrade remains UNKNOWN. `IsEquippableItem=true` is a separate current-player signal, not full eligibility. Weapon skill lines are preserved as observations and do not prove proficiency. Binding APIs returned false and bindType was 0 in this capture, but their transfer semantics remain unvalidated. Bank remains UNKNOWN.

## Cross-character assessment

`get_forever_gear_allocation` and `GET /api/characters/:identityKey/forever-gear-allocation` are a read-only decision-support view over the Forever Dashboard import context. AccountContext embeds the same core result under each Forever character in AccountContext schema 6. The selected recipient includes its latest observed class, level, equipment, and freshness. Potential item sources preserve their source character, carried/bank completeness and timestamps, exact item variants, carried locations, and binding facets. Carried location is not promoted into an ownership claim; ownership and transferability remain UNKNOWN.

The result keeps eligibility, suitability, upgrade status, transferability, and allocation priority independent. A product-facing `allocationPlan` now projects those same assessments into `EQUIP_CANDIDATE`, `KEEP`, `POSSIBLE_OTHER_CHARACTER`, `NOT_AN_UPGRADE_ON_OBSERVED_METRICS`, or `INSUFFICIENT_EVIDENCE` rows with the exact variant, source location and freshness, recipient, comparison, provenance, reasons, and observations that could change the result. These are review outcomes, never equip/transfer commands. The real Hallo candidate produces `INSUFFICIENT_EVIDENCE`; its lower raw DPS is a limited comparison, not an overall upgrade verdict. Characters in one Dashboard import context are not asserted to share a WoW account. Presence in another character's inventory is not access or transferability. Unobserved bank rows are not enumerated, treated as empty, or ranked. No opaque score or transfer action is generated.

The allocation screen now evaluates each source candidate against every Dashboard-known Forever recipient's freshest class/level, complete equipment slots, and exact equipped item-stat vectors. It reports `EXCLUDED`, `LOCAL_REVIEW`, `POTENTIAL_GEAR_FIT`, or `UNRANKED` with per-character explanations. It does not rank these screens: the roster is not verified as one WoW account, cross-character item usability cannot be queried remotely, and no supported comparable allocation-priority basis exists yet.

Forever rule adapters in `packages/core/src/foreverGearRules.ts` implement the nine Classic-class armor progression table and exact positive-rank weapon-skill-line matching as `CLASSIC_DERIVED_HYPOTHESIS` results. These can screen candidates but cannot establish eligibility; item-specific class restrictions remain UNKNOWN because the captured item-info tuple has no structured allowed-class list. Fresh direct level failures and complete explicit class-denial evidence can exclude; a positive result still requires all relevant gates.

The collector now records the documented Forever `C_PlayerInfo.CanUseItem(itemID)` boolean separately from `C_Item.IsEquippableItem`. Both are current-player-only; neither is reused for another character, and a positive value does not itself establish which restrictions were checked. It also preserves raw `GetItemInfo` bindType and optional `C_Item.IsItemBindToAccount` / `C_Item.IsItemBindToAccountUntilEquip` calls. Binding classification is gated until those specific API semantics are observed and validated on Forever 70291. `isBound=true` alone is not proof of soulbinding; account-bound and ordinary soulbound states remain UNKNOWN until differentiated.

## External API research used

The 2026-10-09 implementation pass checked version tags and contracts in the [Warcraft Wiki `C_Item.GetItemInfo`](https://warcraft.wiki.gg/wiki/API%3AC_Item.GetItemInfo), [`GetItemInfoInstant`](https://warcraft.wiki.gg/wiki/API%3AC_Item.GetItemInfoInstant), [`GetItemStats`](https://warcraft.wiki.gg/wiki/API%3AC_Item.GetItemStats), [`GetItemStatDelta`](https://warcraft.wiki.gg/wiki/API%3AC_Item.GetItemStatDelta), [`GetItemSpecInfo`](https://warcraft.wiki.gg/wiki/API%3AC_Item.GetItemSpecInfo), [`IsEquippableItem`](https://warcraft.wiki.gg/wiki/API%3AC_Item.IsEquippableItem), [`GetSpecialization`](https://warcraft.wiki.gg/wiki/API%3AC_SpecializationInfo.GetSpecialization), and [`GetSpecializationInfo`](https://warcraft.wiki.gg/wiki/API%3AC_SpecializationInfo.GetSpecializationInfo) pages. These pages list Forever 1.60.1 for the relevant APIs. They informed tuple cross-checking, exact-link handling, the distinction between item type/equip-location and character eligibility, and separation of raw stat data from recommendations. The API documentation reports delta results but does not specify direction; a community ClassicAPI implementation suggests item2-minus-item1 but is not Forever evidence. The evaluator calibrates against direct exact-item GetItemStats arithmetic and otherwise leaves delta meaning UNKNOWN.

The latest Hallo capture directly confirms the GetItemInfo tuple length, exact hyperlink, selected tuple/GetItemInfoInstant agreement, raw GetItemStats tables, sampled GetItemStatDelta arithmetic, GetItemSpecInfo return behavior, active specialization identity, and the surprising `IsEquippableItem=true` result for projectile ammunition. GetItemSpecInfo returned no specialization tags for 35 items and one empty table for three; active specialization was Hunter ID 1485, but no talent build was captured. API documentation does not turn these observations into class restrictions, effective stats, talent builds, or transfer routes. `C_Container.GetContainerItemInfo.isBound` is an observed per-container bound facet; false does not establish recipient access or a route. The GetItemInfo `bindType` slot remains raw rather than a transfer conclusion. The Wiki's [binding guide](https://warcraft.wiki.gg/wiki/Binding) describes game rules generally; it does not prove transferability for a particular Forever item or account route.

[Blizzard's UI source](https://github.com/Gethe/wow-ui-source) was checked for item-loading patterns; its current `ItemMixin` treats several item fields as cache-dependent and supports asynchronous continuation. That current source is not the Forever 1.60.1 source tree, so its load behavior is a caution, not a target-client contract. [Pawn's comparison code](https://github.com/VgerMods/Pawn/blob/main/Pawn.lua) uses explicit equipment-slot mappings and separate Classic handling, while its [license](https://github.com/VgerMods/Pawn) is CC BY-NC-ND 3.0. No Pawn code or slot rules were copied. The implementation preserves raw item facts and provides synthetic-tested slot aliases and hand-conflict checks. Weapon proficiency and build conclusions remain hypothesis-labeled or UNKNOWN until validated for Forever.

## Identity and version safety

The source character GUID is checked across imported snapshots. Missing or conflicting GUID history withholds source observations. The model is hard-gated to Forever 1.60.1 build 70291 / interface 16001; other versions do not enter this evaluator. Retail gear-allocation logic is not called.

## Live-validation boundary

Automated fixtures validate candidate-source resolution, freshness, slot mapping and hand conflicts, stat-vector arithmetic, stat-delta calibration, eligibility and contradiction handling, specialization tag comparison, binding/location provenance, allocation-plan dispositions, UNKNOWN handling, same-name realm separation, REST/AccountContext consistency, and MCP contracts. The real Hallo and Natokni SavedVariables records were imported through the normal import route into a temporary development database; REST, AccountContext, and MCP returned the same allocation plan. Hallo contributed one item with exact API evidence. Natokni had eight observed carried rows but no item API rows, so the plan preserves sixteen character/item recipient pairs as INSUFFICIENT_EVIDENCE. The opt-in `[LIVE REGRESSION]` test reads these SavedVariables without modifying the file. Effective stats, weapon-speed comparisons, Forever class/proficiency rule mappings, account membership, transfer routes, and cross-character priority remain UNKNOWN. Raw stat dominance is a possible recorded-stat signal, never a confirmed upgrade.

The allocation screen evaluates observed carried candidates and also retains inventory rows whose exact item API evidence is absent or malformed as INSUFFICIENT_EVIDENCE plan entries. It evaluates candidate rows against known Forever recipients using each recipient's own level, class, equipment, and skill observations. It preserves exact item variants and labels derived screens separately from hypotheses and unknowns. Cross-character possibilities remain unranked and transferability UNKNOWN because the Dashboard does not record a validated account identifier or transfer route. The same SavedVariables file already contains Hallo and Natokni, but they are on different realms; together they exercise source identity, missing item metadata, and recipient screening. No additional leveling or crafting is needed for that validation. A same-realm second-character capture could improve realm-specific coverage, but no recipe or profession scenario is currently recommended; it would not resolve the missing account-membership or transfer-route evidence.
