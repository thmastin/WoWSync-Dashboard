## Phases 58-59 - cross-project reservation and procurement planning

The portfolio manual-work session can now attach a player-selected reservation quantity to each selected requirement. The reservation and its PLANNED work order are written in the same all-or-nothing SQLite transaction across the selected active projects. The server and transaction recheck the exact need/evidence snapshot, explicit version and source, recent freshness, fully quantified complete source sections, per-need remaining requirement, and aggregate availability across every selected request. Requests that exceed the observed unreserved lower bound, overlap a base `ITEM_ID` with an exact `ITEM_REF`, exceed a need, or depend on incomplete/unknown storage fail without changing any project. Same exact resource scopes aggregate once; distinct exact item variants remain distinct according to the existing reservation rules. A reservation is a plan commitment, not a lock or inventory operation.

For a `PURCHASE` work order, the same session can now save the existing structured procurement contract when the item requirement names the assigned same-version character as both source/buyer and intended recipient. The player supplies a positive copper ceiling. The ceiling is linked to the requirement, but does not claim market availability, a current quote, affordability, or a purchase. Requirements without this explicit buyer/source/recipient identity remain eligible only for a generic conditional manual purchase step.

The synthetic multi-project browser scenario now rejects two requests that would reserve more than the same observed quantity, confirms no partial writes, retries within capacity, carries a structured purchase ceiling, and checks that REST, AccountContext, and MCP agree. A later fixture observation below the saved reservations raises the reservation review while leaving work PLANNED; it does not infer that any action occurred. Server tests also cover base-item/exact-variant collision across different projects that happen to reuse the same local need ID, plus UNKNOWN bank rejection. These tests do not establish live-game or production behavior. See `ERP_CHECKPOINT_20261010_PHASE58-59.md`.

## Data and APIs

- SQLite stores one version-scoped project document in `erp_projects`, with an optimistic revision number. Schema changes are additive.
- Writable Dashboard/import initialization creates `erp_projects` and `erp_project_events`; as with other required tables, a legacy database opened directly by the read-only MCP consumer fails closed until the normal writable initialization path has created the additive schema.
- Every successful create/update writes an atomic append-only revision event in `erp_project_events`. It records changed field names and status transitions, not full prior project text or inferred game outcomes. REST/UI expose the 50 most recent events and an explicit total/truncation flag; the backing ledger retains the full event sequence. AccountContext schema 20 carries project revision, event count, compact work-order readiness/reconciliation/planned-output/procurement state counts, and version-scoped possible-source screening counts from the shared core projection.
- Work-order readiness is a read-time projection shared by REST, MCP, and UI. It checks explicit dependencies, linked needs, active reservations, and repeated linked quantities. Equivalent linked needs sharing an explicit source are aggregated; base-item/exact-variant ambiguity fails closed. Current complete item shortfalls may surface as a player-reviewed GATHER/PURCHASE step; unsupported, stale, incomplete, or non-item shortfalls still block. A procurement spending ceiling is upper-bound intent, not a resource need or readiness blocker. Readiness never executes an action or implies access, eligibility, upgrade value, craftability, gathering routes, purchase availability, or price.
- `ErpResourceNeed`, `ErpReservation`, and `ErpWorkOrder` represent intent. They are not observations or proof of possession. A need chooses exactly one explicit character source or, for Retail only, one shared storage owner key.
- `GET/POST /api/versions/:version/erp/projects`, `PUT /api/versions/:version/erp/projects/:id`, and `PATCH .../:id/status` serve the Dashboard. The core validates supported versions, explicit character identities, dependency graphs, quantities, and required completion notes.
- MCP exposes a read-only, version-scoped `get_erp_projects` page (10 by default, at most 20) through the existing read-only store. It returns page totals/truncation; each project exposes up to 50 recent revision events. Mutations remain in the local Dashboard UI/API.
- AccountContext schema 20 includes compact project/revision, readiness, progress, planned-craft-output, procurement-quote, recorded-gold-reservation, quote-versus-recorded-gold, and assigned-gatherer observation state summaries while detailed, evidence-qualified needs and work-order reconciliation remain available from the same core read model used by REST and MCP.
- Work-order progress is a read-time evidence projection. Player completion remains explicit intent; current linked resource state, observed changes, and unresolved evidence are separate. A changed quantity never proves a work-order cause, and current resource coverage never auto-completes a task.

## Evidence rules

Character projections use only the explicitly selected character's evidence. Supported supply checks are exact itemString, declared base item ID, gold in copper, observed profession skill by exact profession name, explicitly observed character-scoped Retail currency IDs, and an exact explicitly reported Retail learned-recipe state. A listed zero currency quantity is an observed zero; a currency absent from the list is UNKNOWN. Account-wide currency balances do not establish character access and remain UNKNOWN for character needs. Currency evidence in other versions remains UNKNOWN until those versions have supported structured captures. Recipe catalogs are partial: only an exact current learned-state row can report learned/not learned. Missing rows stay UNKNOWN, historical rows stay LAST_SEEN, and other versions remain unsupported. Learned state does not establish current skill, unlock conditions, reagent supply, or craftability.

Retail item needs may instead select one explicit shared-storage owner key. The evaluator reuses the immutable Warband/Guild observation projection; exact item variants are preserved. A complete absence can establish a source-scoped shortfall only when coverage is exhaustive. Partial, inaccessible, unconfirmed, conflicting, and LAST_SEEN evidence remains UNKNOWN or potential. Warband is installation-local rather than a Battle.net account identity. Guild holdings remain guild-owned. A positive source quantity identifies location and quantity but never proves character access or a transfer route.

Item quantity uses only exact matching rows. UNKNOWN sections and unknown row identities/quantities remain unresolved. A potential LAST_SEEN quantity never becomes current supply. A shortfall is definitive only when both personal bags and bank are OBSERVED and marked complete; enough directly observed quantity can establish a lower bound even when another section is unknown. Character gold keeps its own state and timestamp.

Resource changes compare adjacent imports for the same explicit character. Item deltas are per storage section and require complete OBSERVED rows with known identities and quantities; gold deltas require OBSERVED character sections. Deltas say only that an observation changed. They do not attribute a transfer, purchase, craft, or project action.

Reservations are explicit planning claims, never inventory mutations. Active reservations aggregate across projects only when version, explicit source character or owner, and resource scope overlap. Character inventory cannot consume a Warband/Guild reservation, and those owner scopes cannot consume each other's reservations. Exact item variants remain distinct; a base-item reservation overlapping an exact variant makes the assessment UNKNOWN because quantities cannot safely be reconciled. Work-order readiness aggregates repeated linked claims from one source and subtracts competing active reservations while treating reservations attached to that work order as its own intent. Progress does not claim observed units are independently available when another linked need or reservation overlaps. Partial/unobserved storage prevents an over-reservation conclusion when unseen sections could contain supply. Profession/recipe capability is not quantity-reservable. Currency reservations are enabled only when the source has an observed character-scoped Retail balance; account-wide currency is not assigned to the reporting character. Reservation is intent, not account membership, transfer access, or a physical lock.

An item need with an explicit intended recipient also receives a same-version source screen across other imported characters. It preserves exact matched `itemString` variants even under an explicitly declared base `ITEM_ID` search, shows bag/bank section provenance, timestamps, freshness, partial-scan lower bounds, and existing reservation overlap, and omits characters with no positive observed or historical match. Base-ID search groups variants for discovery only; it does not establish their interchangeability. Candidate output is capped at 25 per need with the full candidate count and truncation state exposed. This is a location lead only: roster membership does not establish account membership, cross-realm access, ownership, or transferability. A player may record a displayed character as the planned source; this is saved intent, and resulting shortage evidence remains independent. Active reservations prevent source switching until released. REST, MCP, AccountContext, and Projects & Work Orders use the same projection.

From a possible source, a player can create a linked `INVESTIGATE` work order assigned to the intended recipient. Instructions preserve each exact itemString's own OBSERVED/LAST_SEEN state, section, timestamp, and known quantity/lower bound, alongside conservative source freshness and unresolved sections. Active duplicate tasks are recognized; completed or cancelled tasks may be recreated. The task asks the player to refresh and verify location/access/route, explicitly leaves unsupported outcomes UNKNOWN, and does not authorize or execute movement.

Work orders are manual steps. The player can record PLANNED, IN_PROGRESS, or WAITING_FOR_EVIDENCE in the Dashboard; these are saved plan statuses, not game actions or observations. A player-entered note is required to mark a work order or project complete. Inventory changes never auto-complete tasks.

`RETRIEVE` is available as a distinct manual work-order type for a player-planned retrieval from a bank or other observed storage location. It remains separate from character-to-character `TRANSFER` reconciliation. An observed storage row may support resource need evidence, but it does not establish current access, retrieval eligibility, or that a retrieval occurred; the player confirms access and records the outcome manually.

For CRAFT work orders, linked `PROFESSION` and `RECIPE` needs are checked directly against the assigned character's own same-version snapshots, independently of the material need's supply source. The capability result carries its own source identity, freshness, timestamp, and section provenance. A recent observed skill or learned recipe on a different character never satisfies the assigned crafter's check. Missing assignment, missing/stale/unknown assigned-character evidence, and an observed unmet threshold remain distinct. A matching skill/recipe fact is only a prerequisite signal: it does not prove specialization, unlock conditions, reagents, or current craftability. Other linked material needs retain their separate source and reservation scopes.

For a CRAFT step, linked item input needs can also expose adjacent bag/bank section changes when the need explicitly names the assigned same-version crafter as its source. The review preserves exact `ITEM_REF` variants, section quantities, timestamps, latest and earlier freshness, and returns UNKNOWN when source identity or comparable evidence is missing. Input changes and the separately assessed planned output remain non-causal observations: neither proves reagent consumption, a successful craft, or completion. REST and MCP return the detailed core review, AccountContext counts input comparison states, and the workbench presents the evidence together with its limitations.

For a `SELL_MANUALLY` step, an item need explicitly sourced from its assigned same-version seller can be paired with that character's observed item and gold deltas. The review keeps section changes, source identity, freshness, and `CAUSE_UNKNOWN`; inaccessible personal storage, mismatched identities, missing before/after captures, or invalid timestamps do not become a positive sale result. Item disappearance and gold increase remain separate observations and do not establish that a sale occurred, identify a buyer, or attribute proceeds to the item. REST/MCP expose the detailed review, AccountContext summarizes its state, and the workbench presents the observed comparison for player review.

An active `CRAFT` step with no linked profession or recipe requirement remains `WAITING_FOR_EVIDENCE`, even when its listed materials are observed. Link the exact known prerequisite need to screen that fact; material coverage alone is not craft readiness. Existing reservation conflicts remain visible before this missing-prerequisite result.

Project history records saved intent changes, including resource needs, reservations, work orders, title/objective, priority, and status. Observation deltas remain a separate evidence view, explicitly non-causal. History never asserts that a described player action happened in game.

When adding a manual work order, the player can link resource needs and prerequisite work orders. A readiness projection makes those recorded relationships visible and conservatively gates the workbench wording; it is not an automatic scheduler or game-action authorization.

For a `TRANSFER` work order with an item need and explicit character source and destination, progress can compare each character's adjacent, recent, complete observations for the declared item scope. The result reports only which side's observation changed, with section quantities, timestamps, and freshness; it is always `CAUSE_UNKNOWN` and does not establish a transfer, ownership, access, or account membership. A broad base-item (`ITEM_ID`) comparison may include different variants and calls that out explicitly. If the need selects a shared-storage owner, a work-order character source cannot override that scope: the paired review is an identity/scope conflict and does not compare that character's inventory as owner evidence. Without an explicit character pair or comparable evidence, the result remains UNKNOWN. REST, MCP, and the UI read the same projection.

`PROVISION` work orders now expose the same paired section-level comparison under a separate `provisioningObservationReviews` field and UI section. Both explicit character identities must match the project version; conflicting or shared-owner source scopes fail closed. Changes remain non-causal, access and account membership remain UNKNOWN, and the saved work order is never completed automatically. This is a player review of observations, not evidence that an item was moved or received.

`RETRIEVE` work orders with an explicit same-version character and item need compare that character's adjacent complete bag and personal-bank observations. For an explicit Retail Warband or guild owner, the projection can instead compare that owner's own adjacent complete live snapshots from the immutable owner journal. It preserves the owner key and carrier-export identities; carrier identity does not establish account membership or owner access. A newer partial observation, tied conflicting history, unidentified item row, stale/future timestamps, or inaccessible/unconfirmed guild tab leaves the comparison UNKNOWN. REST and MCP expose `retrievalObservationReviews`; the workbench distinguishes personal from shared-owner evidence. Even a recent bank decrease paired with a bag increase, or shared-owner content change, is `CAUSE_UNKNOWN`: it does not establish retrieval, access, ownership by a character, transfer route, or player action, and never completes the work order. AccountContext retains its compact reconciliation-state summary over the same core projection.

Manual work-order authoring also accepts player-entered instructions and explicit source, destination, and assignee character identities. These fields document intent and expected context only; they do not establish account membership, possession, accessibility, or transferability. Project history records task status transitions by stable work-order ID, rendering old events without the optional transition detail remains supported, and the UI labels these as saved plan status. No action is dispatched to the game.

CRAFT work orders may also carry a player-declared planned output (`ITEM_ID` or exact `ITEM_REF`, label, positive quantity). This output is not a learned recipe result, input need, reservation, or observed supply. The read-time assessment checks only the one explicitly assigned character or, when no assignee exists, the explicitly named destination; if both are present and differ, the assessment is UNKNOWN. The result preserves source section, timestamp, completeness, freshness, current versus LAST_SEEN quantity, and adjacent-observation change. Appearance or change is always non-causal; it never proves crafting or completes the work order. REST/MCP expose the detailed assessment, AccountContext schema 20 exposes compact per-project state counts, and the existing workbench shows the declared result beside its evidence. Legacy work orders without this optional field remain valid.

PURCHASE work orders may link an explicit same-character item target and store a positive integer copper spending ceiling as plan metadata. The ceiling is upper-bound intent: it is not a GOLD_COPPER need, commitment, or reservation. The assessment reports current item coverage/shortfall and gross observed copper versus the ceiling separately. The player may record a checked quote as a total copper amount for an explicit quantity, plus an optional source note; it is explicitly `PLAYER_REPORTED`, timestamped, and freshness-labelled. No unit-price extrapolation is performed, and the quote is not a verified market feed. The procurement assessment also totals only explicit active WoWSync GOLD_COPPER reservations scoped to that buyer and version. Where gross gold is recent and covers those recorded reservations, it reports a derived snapshot remainder; if there are no recorded reservations, the gross snapshot is the comparison remainder. A player quote is compared only when both records are recent and the gold snapshot timestamp is strictly later than the quote timestamp; equal-second timestamps are not treated as ordered. Otherwise the result is `EVIDENCE_NOT_COMPARABLE`. The comparison says only whether the entered total falls above or below the dated gross snapshot remainder after recorded reservations. This is an incomplete planning ledger, not actual spendable balance or affordability. Missing/stale inventory or currency preserves UNKNOWN. Current stock availability, purchase routes, accessible sellers, unreserved spending power, and affordability always remain UNKNOWN. REST/MCP return the detailed assessment; AccountContext schema 20 summarizes item-gap, quote, recorded reservation, and quote/gold comparison states. The workbench records quotes and reservation context as planning evidence, not a recommendation or action. It does not reserve a price, execute a purchase, or claim one occurred.

## User workflow

For a GATHER work order, an explicitly assigned same-version character and a need sourced from that same character can show the item quantity delta in complete, recent OBSERVED bags. Bank sections are excluded from this gatherer-specific comparison. Stale, partial, future-dated, unordered, missing, or mismatched evidence remains UNKNOWN. A bag increase or decrease is non-causal and never completes the task. REST, MCP, AccountContext and the workbench share the core projection.

For a PURCHASE work order with its required same-character item target, the read-time progress view pairs two independent observations: the buyer's character-gold delta and the target item's per-section quantity deltas. Each side retains its own freshness; historical deltas remain visible as stale, and a missing comparable item section remains UNKNOWN. The pair is descriptive only: neither change is attributed to purchasing, a seller, or this work order. REST, MCP, and the workbench expose the same core projection; a single snapshot reports no invented before/after item change.

Open **Projects & Work Orders** from a version tab. Create a project, add an explicit resource requirement and source character or observed Retail shared owner, record a manual task, and optionally reserve a quantity from directly observed supply. The UI shows evidence date/freshness, current versus historical coverage, cross-project reservations, and section-level changes since the previous complete export. A reservation can be explicitly released. The feature never issues equip, transfer, mail, bank, craft, purchase, or sell operations.
